# RepoLegibility

Shows what a C# repo's code reads, writes and runs, and how clearly.

A WPF desktop tool (.NET 10, single self-contained exe, dark mode throughout). Open a repo zip, or drop one on the window, and every place the code touches the outside world is listed: files, the registry, the network, processes, accounts and credentials, reflection, loaded code, native calls. Each finding says how far it reaches and how legible it is: whether the source shows it, leaves it to run time, can't show it, or hides it, and where the scan stopped when it couldn't tell. The zip is read in memory: nothing in it is extracted, built or run.

It's meant for anyone about to build or run someone else's code, expert or not: a few minutes with the report tell you what the code can do, and which few passages to read closely before you trust it.

## What this is for

RepoLegibility was made for my own repos: to make them legible to people who don't read C#, and to experts short on time. On those repos it holds up. It shows what the code reads, writes, sends and runs, where each of those places comes from, and where the source doesn't say.

## What it can't do

It can't decide on its own whether a repo is safe. A repo can hide what it does on purpose, and some things only become known while it runs. A "No" in the Overview means nothing of that kind was found, not that there is none. What it gives you is insight you otherwise wouldn't have: where to look, what to ask, and what the author should have told you.

It reads C# without compiling it, so on code written very differently from mine it can miss things or follow a name to the wrong place. When a finding looks wrong, the trace shows how the scan got there.

To see what a repo built to be caught looks like, scan `shady-demo.zip`: a small test repo that does everything a report should flag, made so it can't be built or run.

## Why RepoLegibility?

With AI writing more and more code, trusting a repository now means trusting everyone and everything involved:

- that the AI didn't make a crucial mistake
- that the person directing it acted in good faith
- that no one involved had malicious intent
- that the code you received is actually the code that was meant to be delivered, untouched by toolchain or supply-chain attacks

A signed binary settles part of this: it tells you who most likely released something. It doesn't tell you what the code does, or whether it was built in good faith.

RepoLegibility doesn't solve that problem entirely, and doesn't claim to. It gives you a head start.

### For users evaluating a repo

RepoLegibility reads the C# source code and answers the first questions anyone asks, whether you're a non-specialist or an expert short on time:

1. What does this app touch on my machine and on the network?
2. Does it ask for administrator rights, and what does it reach with them?
3. Where should I (or someone I ask) start looking when reviewing the code?

It works backwards. It starts from each point where the code touches your system: a file, a registry key, a network address, a program it starts, a credential. From there it traces where the target comes from: a fixed path, a setting, what the user types, or something the code hides. Each finding gets a scope (the app's own folder, your user profile, the whole machine, a web service) and a legibility:

- **Clear:** the source shows what happens and where.
- **Run time:** the action is known; the target is decided when the app runs, and RepoLegibility says by what.
- **Untraced:** the trace stopped before it found where the value comes from; RepoLegibility shows where it stopped.
- **Opaque:** the source can't show what happens, by nature: a name computed at run time, code loaded from bytes, a command built from settings. A "who decides" line says what does: the app's settings, you, a file, how the app is started, or a server on the internet.
- **Obscured:** the source holds it, but written so it can't be read: Base64, character codes, short fragments, XOR, an encoded PowerShell command. That's a choice someone made, so these come first, in red; where the source fixes the value, the scan works it out without running anything and shows it.

Neither Opaque nor Obscured is a verdict: honest code uses these techniques too, and only reading the code tells which it is.

Every scan records the SHA-256 of the archive it read, so you know exactly which version of the code the results describe. Build the app from that same archive and compare the result byte for byte with the release: if they match, the report describes the program you run.

This won't tell you whether the code is well written. It tells you what the code involves, so you can make an informed decision about whether to use it. Either way, it's good practice to try unfamiliar software in a VM or another isolated environment first.

### For developers

Run RepoLegibility on your own project to see which parts look opaque or untraced to an outside reviewer. Making those sections more legible makes your repo easier to trust.

RepoLegibility covers the basics. For a deeper check, follow up with a full security review. "Copy for AI" exports the findings with the code around each one, so you can hand them to an AI assistant as a starting point. The PDF report gives the same to a person.

### What RepoLegibility can't do

- **Managed C# only.** It analyses managed C# source, reads XAML for event wiring, and checks project files, build scripts and CI workflows for steps that download or run things. Native code, calls into unmanaged libraries and other languages are outside its view; it shows where the C# code hands off to them, but not what happens after that.
- **Dependencies are listed, not read.** It names every NuGet package and CI action the repo pulls in, and whether the actions are pinned, but the code inside them is outside its view. For a supply-chain review, those are the next place to look.
- **Binaries are listed, not read.** DLLs, executables and archives in the repo are named with their SHA-256 as black boxes.
- **Code fetched or generated at run time isn't in the source.** RepoLegibility flags the places where the code loads, compiles or starts something it brought in itself; what that something does stays unknown.
- **Opaque points, it doesn't resolve.** It can't say what a computed name or a decoded string will turn out to be.
- **Traces have limits.** Each touchpoint is followed back at most 12 steps deep and 120 in all. Some paths can't be followed from the source at all: a method only a framework or an interface calls, a value passed on as a delegate, reflection. Where a trace stops, RepoLegibility shows where and why.
- **It reads; it doesn't compile or run.** Names are matched by name, not by type, so a trace can now and then pass through a same-named member of another class. Nothing in the repo is executed.

What it reports is a map of what the code involves, not a verdict on whether it is safe.

## Two questions per finding

**How far does it reach? (scope)**

Scope is a ladder, mildest first, and its tag's colour climbs with it.

| Scope | Colour | What it covers |
| --- | --- | --- |
| App | Green | The app's own folder and files. |
| User | Neutral | The user's profile, documents, HKCU, temp folder, the user's credentials: anything the user can reach. |
| Web service | Amber | Remote endpoints, and what is sent to them: it leaves the machine. |
| Admin | Red | What only an administrator can do: change HKLM, HKCR, Program Files or the Windows folder, install or control services, change the firewall, start a program elevated, read the SAM or SECURITY hive. Reading a machine-wide place any user can read is User. |

**How legible is it?**

| Legibility | Meaning |
| --- | --- |
| Clear | The source shows what happens and where, however many steps it takes to follow; a long way is noted ("Followed over 21 steps in 5 files"). |
| Run time | The kind of action is known; the target is decided when the app runs, and the reasons say by what: settings, the command line, what the user types or picks, files found in a folder, a property set by binding. Code built from an expression tree counts here too: what runs is put together while the app runs, from parts the source shows. So does one of GitHub's own CI actions pinned to a tag: what runs is decided outside this repo. |
| Untraced | The scan didn't reach where the value comes from. That's not a verdict on the code: the reasons name the dead end (a parameter of a method nothing in the repo calls, a value passed on as a delegate, a lambda parameter, or the step limit with nothing known yet, with the file and line where it stopped), and the whole member is shown so you can take it from there. A target the scan couldn't trace reads "not traced". |
| Opaque | The source can't show what happens, by nature: names looked up by reflection from computed strings, code loaded from bytes, shell commands assembled at run time, a third-party CI action not pinned to a commit. Reflection that can only reach the app's own type, made right there (`current = new Config(); current.GetType().GetProperty(name)`), and the app's own types its properties declare, is Run time instead: the source shows everything it can reach, only which one is picked while it runs. "Who decides" says what does. These are passages to read yourself. |
| Obscured | The source holds it, but written so it can't be read: values decoded from Base64 or built from character codes, short fragments, XOR or reversed text (`new string(s.Reverse()…)`, `string.Concat(… .Reverse())`; reversing a list or a range slice like `path[..i]` isn't hiding anything), encryption, encoded PowerShell. Red and ranked first: someone chose to make it hard to read. Where the source fixes the value, it's worked out and shown, marked **(decoded)** or **(assembled)**. |

### Keys

Every finding has a key such as **N-3f2a1c** next to its #n. The #n is only its place in this list; the key stays the same when the same zip is scanned again and when code elsewhere changes, so two reports, or feedback on one, can point at the same finding. It comes from the finding's kind, file, method, call and which occurrence of that call in the method it is, not from the line number. Renaming the file, the method or the call gives a new key. The letter says the kind: F files, R registry, N network, P processes, C code (reflection, loading, native, COM), A accounts and secrets, B build and CI, E elevation, O other. Search finds a finding by its key.

### Marks beside the legibility

- **Hidden on purpose**: the author hid the value: Base64, character codes, short fragments joined together, XOR, reversal, encryption, encoded PowerShell. Such a finding is **Obscured**, and the mark says how. Where the source fixes the value, RepoLegibility works it out without running anything (`"ht" + "tp" + "s:" + "//" + "x.io"`, `new string(new[] { 'S', 'y', … })`, Base64 decoded as text, `powershell -enc …`) and shows it, marked **(decoded)** or **(assembled)**; the finding stays Obscured.
- **Not used in this source**: declared, looked up or created, but not used in this source: a `[DllImport]` nothing calls, a COM type looked up but never created, a method looked up by reflection and never invoked, a credential made and never passed on. Something the code can do, not something it does; it ranks below what's used.
- **Not called by the app**: only tests reach the code it sits in. Where the test's call shows it, the finding says what the test passes in ("Tests call SortDictionary with: temp folder › …"), marked as the test's value.
- **Direction**: which way it moves things. **Reads** (takes in from this machine), **Changes** (changes this machine; named apart from the header's Writes pill, which counts file and registry writes only), **Sends** (data leaves the machine), **Receives** (data comes in from outside), **Runs** (starts or loads code). A POST sends and receives. For a request that sends something, the source's personal data is named where it shows: "Sends: the Windows user name".

## What it looks for

| Area | Found |
| --- | --- |
| Files | Writes, copies, moves, deletes, reads, folder listings (`File.*`, `Directory.*`, streams, `ZipFile`, `Save(path)`); media it plays (`MediaElement.Source`, `MediaPlayer.Open`, `SoundPlayer`), a download when the source is a web address |
| Registry | Keys and values read, set and deleted, with the hive; Run keys, policies and Classes are noted, and so are the SAM hive (local accounts' password hashes) and the SECURITY hive (the system's stored secrets) |
| Network | HTTP requests, `WebClient`, `WebRequest`, TCP and UDP, DNS, SMTP, ping; listeners and web servers |
| Databases | Connections and how they log in |
| Processes | `Process.Start` with the program and its arguments; `runas` elevation; tools that change machine settings (`netsh`, `sc`, `schtasks`, `reg` …); PowerShell run in-process. "Opens … in the browser" only where the source shows it: every value is a web address with a fixed host (a method that returns only such addresses counts, so `Citations.UrlOf` gives "Opens web pages on www.unicode.org, www.w3.org … in the browser"), or the code checks for http or https in an `if` the start depends on, directly or through a property of the repo's own that makes that check (`if (detail is { IsWebAddress: true })`). A name like `url` proves nothing, since Windows opens whatever it's given; without proof it reads "Hands a value to Windows to open", with a note on what that can do. Links of kinds Windows hands to handlers that have been abused (`ms-msdt:`, `search-ms:` …) get a note of their own. A folder or file opened with `UseShellExecute = true` reads "Opens the exe folder in Explorer" or "Opens … with the program Windows has for it"; the app's own exe (`Environment.ProcessPath`) reads "Starts the app itself again" |
| Elevation | `requireAdministrator` / `highestAvailable` manifests, `runas`, administrator checks; privileges the code turns on (`SeBackupPrivilege`, `SeRestorePrivilege`, `SeDebugPrivilege`, `SeTakeOwnershipPrivilege` …), each with what it lets the process do |
| Identity and credentials | Logins (`NetworkCredential`), tokens and API keys sent in headers, the current user's Windows login (`UseDefaultCredentials`, `CredentialCache.DefaultCredentials`; named as the proxy's where it's set on a proxy), impersonation, starting a process as another account, DPAPI, Credential Manager, certificate stores, Windows services |
| Secrets | Tokens, keys and passwords written into code or configuration, shown masked |
| Reflection and loaded code | Types and members looked up by name, `Assembly.Load`, native libraries, generated and compiled code, expression trees turned into code (`.Compile()`) |
| Native code | Every P/Invoke declaration, one finding per library ("advapi32.dll: 12 functions, 3 not called in this source"), each function listed with where it's declared, so search finds it by name; input hooks, other-process access and privilege APIs are flagged, and functions with a plain meaning say it (`SHOpenWithDialog`: the app the user chooses starts with the file; `RegLoadKey`: a hive mounted for everyone until it's unloaded; `RegSaveKeyEx`; `ShellExecute`, `CreateProcess`). Those that start programs are listed under Programs in the Overview |
| COM, WMI, event log, environment, clipboard | Including the Windows Firewall and Task Scheduler through COM |
| Embedded data | Long Base64 strings and large byte arrays in the code |
| Build | `<Exec>` steps, inline build tasks, downloads and imports from outside the repo in `.csproj`, `.props` and `.targets` |
| CI | `.github/workflows`: third-party actions and whether they're pinned to a commit, `run:` steps, the secrets they use |
| Scripts | `.ps1`, `.cmd`, `.bat`, `.sh` and `.vbs` files aren't C# and aren't followed, but a line that downloads code and runs it, or runs an encoded command, is listed as opaque |

A property bound to a list's selection in the XAML (`SelectedItem="{Binding SelectedA}"` on a ComboBox, ListBox, DataGrid …) is what the user picks there: the target reads "picked in a list (SelectedA) › …", the reasons and "Who decides" name the list's file and line, and where the scan can tell, what the list offers (what's found in a folder while the app runs, or values written in the source, from what the code adds to its `ItemsSource`). It's Run time, like a file the user picks in a dialog.

The repo's own wrapper around a .NET place is followed to it: `AppPaths.BaseDirectory => AppContext.BaseDirectory` is the exe folder, wherever it's used. A path under the app's own folder whose rest a setting names, or that the trace couldn't follow to the end, is User scope: a full path there can point anywhere.

The system drive's root (`Path.GetPathRoot(Environment.SystemDirectory)`, or `C:\` written out) is Admin scope: a folder there is shared by every account on the computer, so `C:\SurfaceReducer` reads "the drive's root › SurfaceReducer" under the whole computer, not your account. The root of any other path is just a part of that path.

What the user hands the app is named for how: "a file or folder the user picks" (a dialog), "files the user drops onto the window" (`DataFormats.FileDrop`), and the command line (`e.Args` in `OnStartup`, `args` in `Main`): "a file or folder the user picks, drops onto the window or opens it with (its command line)". A tree walk under such a folder adds ", or what's found inside it". A path the user types keeps that part in front of the rest: "a path the user types › NTUSER-{}.DAT", so a name doesn't read like a fixed system file.

A relative path (`"out.txt"`) is App scope: it lands in the working folder, which is the exe's folder when the app is started by double-click.

Code in test projects is listed separately: it doesn't ship, but it runs on every machine that runs the tests. It's not counted in the header pills.

### How a target is followed

For every call, the argument that names its target (a path, an address, a key, a program) is followed back through local variables, fields, properties, records, `foreach` collections, pattern, `out` and deconstructed variables (`var (a, b) = …`), methods and their `return`s, and through a method's parameters to the places that call it. A value read off a variable (`uri.Host`) follows the variable; the member is looked up by name only when the variable's type is the repo's own, and then only that type's (`set.Folder` on a `ChangeSet set` is `ChangeSet.Folder`, not another type's `Folder`; a variable may be named like a contextual keyword, `set` or `group`). `x.ToString()` follows `x` unless `x`'s own type overrides it. A local function sees the variables of the method around it. A caller counts when the code calls the method by name on its type, on a receiver declared as that type, or through `this` (in its own file too: `Session.Add(key)` on a HashSet field isn't the class's own `Add`, nor is `store.Pins.Add(pin)` on a property that shares the class's name), when its arguments fit that overload, and when XAML wires it as an event handler. A property set in an object initializer (`new Step { Name = … }`) belongs to the type being made, wherever the initializer stands: an initializer of a framework type (`new ShapePath { Data = … }`) isn't a definition of the repo's own property of the same name. A method's returns are followed real values first: six `return null;` don't crowd out the one `return path;`. Records are followed to where they're made, `new Verdict(…)` and target-typed `new(…)` alike. Of `a ? b : c`, only `b` and `c` are followed: the condition only picks one, except what a pattern in it names (`Read(path, name) is { Exists: true } v ? v.Data : ""` follows `Read(…)`, since `v` is what it returns). Inside a call too, a string a condition compares with (`Path.Combine(dir, ext == ".xml" ? "tasks" : "registry")`) is never one of the values. A variable introduced later in the same statement (`d.TryGetValue(k, out var u) ? u : null`) is followed to where it's set; the key of such a lookup only picks the entry. A collection is what's put into it: `files.Add(path)`, `AddRange`, `Insert`, `stack.Push(d)`, `Enqueue`, anywhere in the method. A `foreach` over a method of the repo follows what it returns or `yield return`s. A field of a tuple (`m.Label` on a `List<(…, string Label)>`) follows the tuple, never another class's `Label`; a pattern variable (`cb.Tag is ValueTuple<…> t`) follows what was tested; a WPF `Tag` follows what the file puts into the Tags of that kind of element; type arguments (`new List<(RegistryHive Hive, …)>()`) are never values. Strings are shown as the program sees them: `"C:\\Temp"` is `C:\Temp`, `\"` a quote. Plain names met side by side in a list are choices, not folders: "a path the user types › SOFTWARE, SYSTEM, SAM or SECURITY". A hash in a name (`SHA256.HashData`, or a method of the repo's that returns one) is a step of its own: what's hashed changes the name, never where it points, so it isn't followed further, and the target says so ("a file or folder the user picks › a name that includes a SHA-256 of the address"; "made from" when the hash is the whole name). What a `?? throw …` throws isn't the value either. A method the trace enters through a call gets that call's arguments: inside `PathOf(Tool.PowerShell)`, its parameter is `Tool.PowerShell`, not what every other caller passes, and a `tool switch { … }` there gives only the arm that matches. The extra arguments of `OpenSubKey(path, writable: true)` and the like say how a key is opened, not which one, and aren't followed. `System.IO.Path.Combine` and other names spelled out from `System.` or `Microsoft.` are the base library's, never a method of the repo's with the same name. Holes in an interpolated string are filled in where the source fixes them, in their place: a constant, a local set once, a `foreach` or a lambda over a list written out in the source (one element of a tuple too), or the argument of the call the trace came through. One hole with a few values reads as one of them: `SOFTWARE\Policies\Microsoft\WindowsFirewall\DomainProfile (or PrivateProfile, PublicProfile)`. Holes the source doesn't fix stay `{}`. An address sent through an `HttpClient` is joined to its `BaseAddress` only when the source shows it's relative; an absolute address replaces it. The program is a file name where one is written (`FileName = …sc.exe, Arguments = "start TermService"` is "sc.exe start TermService"), a bare word like `start` only where none is. A program started through a helper (`Run(Tool.Schtasks, "/create …")`, `Netsh(args)`, `ToolRunner.Run(item, SystemTools.Reg, new[] { "delete", key, "/f" })`) is a finding per call of the helper, each with its own program and arguments ("reg.exe delete {} /f"), and the reason grades the two apart: the program is fixed, the arguments that are decided while it runs are named. A helper that hands its script to PowerShell as `-EncodedCommand` is encoding for transport, not hiding: each script is shown at the call that passes it, and the start of `powershell.exe` is Clear with a note on the encoding. Only an encoded command written out in the source is Obscured. So `schtasks /create` and `reg import` aren't one finding that names both. A PowerShell script handed to a helper that runs it (`RunPowerShell(script)`) is a finding of its own at each call, named by what its commands do: "removes firewall rules (Remove-NetFirewallRule)". Script files in the repo (`.ps1`, `.cmd`, `.bat`) are named the same way, by their commands or the system tools they call. Well-known system commands, in C#, build steps and CI alike, are described in plain words first ("Turns off Windows Firewall for all profiles": `netsh`, Defender exclusions, `vssadmin delete shadows`, `bcdedit`, `schtasks /create`, Run keys, `icacls … /grant Everyone`, `curl … | bash`, `iex` and others). A call with no receiver means the method of its own class, not a same-named one elsewhere.

Where the source can't say more, the reason says what the value is instead of guessing: a property of a type the app fills from a settings file, named like one (`Config`, `Settings`, `Options`, `Preferences`; `JsonSerializer.Deserialize<Config>`, `new XmlSerializer(typeof(Config))`, `configuration.Get<Config>()`, and the types of its properties one level down) is **a setting**; the app's own saved data (`ChangeSet`, `Pin`), read back from JSON, is a value set at run time, not a setting, named with the type and where it's filled ("ProxyUrl, a setting in Config, filled from JSON at Config.cs:437"); a property set from outside its type (`ctx.TimeStamp = …`) is followed there too, where the variable is declared as that type or only one type has such a property; a start value (`= string.Empty`) counts only when nothing else assigns the property, and then it's filled at run time; `setting.Path`, where the scan can't tell the variable's type and several types have a `Path`, is a property set at run time; a call that passes `null` reaches no file at all; a method only tests call is named as such, and a finding every way to which ends there is tagged **Not called by the app**: the code ships, but in the shipped app it runs only if something outside the repo calls it. A folder listing's search pattern (`Directory.EnumerateFiles(temp, "regdiff_*.hive*")`) filters the names, it isn't a folder: "files found at run time in temp folder matching regdiff_*.hive*". A `foreach` whose body is one statement without braces is followed like any other. What a started program prints (`p.StandardOutput.ReadToEnd()`) is decided while it runs: a folder dism reports reads "a path that a program it starts prints", and the arguments it was started with aren't folders. A count or exit code (`.Count`, `.Length`, `.ExitCode`) is never part of a place. The names a key holds (`GetValueNames()`, `GetSubKeyNames()`) are, like a folder listing, whatever is there when it runs: a key opened by such a name is Run time. A path a Windows event names (`EventLogReader.ReadEvent`, the `Application` field of a Security event) reads "a path a Windows event log entry names": the log's and the field's names aren't folders. The key of a lookup (`data.TryGetValue(k, out var v)`) only picks the entry; it isn't part of what comes out. Text typed into a box the XAML declares (`<TextBox x:Name="TxtProgram">`, an editable ComboBox, a PasswordBox) is what the user types, whatever the box is called. A value read from the registry (`key.GetValue(…)`) is a place decided while it runs: "a value read from the registry (HKLM\…\ProfileList\{} › ProfileImagePath)", the key and value named in brackets, not as folders of a path; a fallback beside it reads "or …". A path shows its root and up to three pieces nearest the file name; "› … ›" marks pieces left out between them. A piece that only fills a name in (`NewFile("failsafe-task", "xml")` into `$"{name}-{stamp}.{extension}"`), a drive letter and a format (`ToString("yyyyMMdd")`, `"N"`) aren't pieces. It stops at a known place (the exe's folder, a special folder, a registry hive, the temp folder, a file the user picks in a dialog, the computer's own name), at a literal, or at something set at run time. A network call whose address comes from a setting, what the user picks or a value set at run time is Run time ("an address from a setting (Url)"); only with nothing known is the address Untraced. A registry helper the whole app goes through (`Reg.Write(path, …)` with a `switch` over hive names) reads "HKLM or HKU … › keys decided while it runs": Run time, with a few of the keys its callers pass, rather than two of them as if they were a path. The steps are listed with each finding, nearest first, so you can check them.

**Names and types.** A capitalised name before a dot (`Path.Combine`, `File.Exists`) is the code's own property only where it's in scope: declared by the type the code sits in, an outer type, or another part of a partial type. Anywhere else it's a type, and only the call's arguments count, even when some other class has a property named `Path`. An unqualified call (`Write(text, ink)`) is a method of the type it's made in, not a same-named method of another class in the same file. A field named with a leading underscore (`_output.Text`) is followed like any variable, and `new() { Text = … }` sets a property of a type it doesn't name, so it never counts as declaring `Text`. `.Text` on a text box, password box or editable combo box is what the user types, whether the box is in the XAML or made in code.

**Values the code builds up.** A collection field that starts empty (`readonly List<string> _tempDirs = new()`) holds what its own type adds to it. A get-only property with a body (`PortableRoot { get { …; return Path.Combine(exeDir, "sdk"); } }`) is read through its getter, like a method, when it gives a place (a string, a URI, a file or folder, or a list of strings); one with a setter, or a WPF dependency property, is set from outside. A `StringBuilder` is followed through the text it's given as plain literals (`args.Append("publish \"")`). What's left out of a value: an `out` argument (`ResolveTempRoot(out _fallback)`), a format (`Guid.NewGuid().ToString("N")`), the name of an environment variable it reads, and an interpolation's alignment (`{x,-10}`). `DriveInfo.GetDrives()` gives a drive's root, found at run time. A search pattern ("matching *.csproj") is shown only when the listing it belongs to is near the top of the trace, not one met deep down on the way to a name.

A path that starts with something decided at run time (what the user types, a pick) isn't relative, so it isn't put in the app's working folder: `Path.Combine(_output.Text, "HISTORY")` is User scope.

**Programs.** A program's target names what it's told to do first (`dotnet.exe publish -c Release`), not names it looks things up by (`GetValue("InstallLocation")`).

**How the report says it.** Each Overview answer lists every finding it speaks of: "Is anything hidden?" names the obscured passages, those the source can't show by nature (in the app and in CI) and those the scan didn't finish; "Does it go on the internet?" names where it sends and, after that, every address it receives from ("Yes: it sends the Windows user name to evil.example (hidden in the code); and receives from 2 more: x.io (hidden in the code) and api.github.com"). The README answer counts the way the headline does: "the 6 things worth knowing together: …; and that it needs administrator rights". Copy for AI lists every key, with no "… N more"; only a long trace is cut, to its nearest 12 steps, and says so. Under "Runs when you start the app", the hidden passages are those in the app's code; the build step is under "Runs when you build". A program started as administrator (`Verb = "runas"`) is a "Starts a process" finding at Admin scope, not Elevation, which is for the manifest and the administrator check. A CI secret in a step's environment is read, not sent. A build or CI step that says what it does says it once ("Runs text as PowerShell code during the build (target Fetch)").

**Web addresses.** The list holds every address the shipped code and its configuration name, and every address the code requests or opens in the browser, even on a host the list otherwise leaves out as documentation (example.org, aka.ms). A database server a connection string names (`Server=db.example.net;…`) is listed too, marked as such; one on this machine (`localhost`, `(localdb)`, `.`) isn't.

**Lambdas.** A lambda's parameter is followed to what the call hands it: the collection for LINQ and list methods (`targets.Where(p => …)`, `Hosts.Select(async host => …)`, through filters and orders that keep the same elements, never through a `Select` that makes new ones) and for `Parallel.ForEach(files, …, file => …)`; the key for `GetOrAdd` and `AddOrUpdate`; and for the app's own method (`s.Table("11", path => …)`), what that method passes where it calls the delegate, also when it hands the delegate on (`=> Build(path, read, …)`). A method handed over as a delegate (`Change(entry, confirm, DictionaryEditor.Pin)`) is followed the same way, to where `Change` calls it. Each lambda's call is followed once per trace.

**Only tests reach it.** Code that ships but that nothing in the app calls, where every way to it ends at tests, says so: its target is "only tests reach it", not "not traced", and it sorts after what the app does. In a helper finding with calls from the app as well, the calls only tests make don't decide its places or its grade; they're counted ("6 calls: 5 run time; 1 more comes from code only tests call").

**XAML.** Only an event attribute wires a method up (`Click="OnSave"`); a button's text (`Content="Save"`) names nothing. `Dns.` counts as a lookup only for `System.Net.Dns`, not for an app's own member named Dns (`ctx.Dns.ResolveAsync()`).

**Helpers.** When the call sits in a small helper that passes its parameter straight on (`void Save(string path) => File.WriteAllText(path, …)`), the finding is the helper's, not one per call: it lists the helper's calls, each judged where it is, and takes the widest scope and the least legible of them. With one call, the finding says where the value is decided. Up to 30 calls are followed per finding; the rest are counted.

It reads the source; it doesn't compile it. Names are matched by name, not by type, so a trace can pass through a same-named member of another class, and a value assembled in ways it can't follow is reported as such, never guessed. A trace follows at most 12 steps deep and 120 in all. When it runs out of steps after it already knows what decides the value at run time, the finding is Run time and the stop is noted; with nothing known yet, it's Untraced. Going deeper rarely helps: where a trace ends, it's almost always at a dead end the source doesn't cross, which is why the reasons name the dead end rather than a number of hops.

## Facts

Beside the findings, the Facts tab lists what helps judge the repo as a whole. It opens with one sentence ("About 101,000 lines of C# in 3 projects, 40 % of them tests. A careful review takes roughly 6 to 13 weeks of full-time reading.") and groups the rest by the question it answers: how big is it (with one bar for app code, tests and comments, and the largest files with a bar for their size), how it's built (each project with what it turns into), what comes from outside, and what the scan covered. Rows that would only say "none" or "0" are left out. Every large file and every project with findings has a button that opens them, all of one width; rows without findings keep the button's room, so the list stands evenly. Web addresses carry the globe icon, black boxes the file icon. The PDF follows the same groups. In detail:

- **Size**: files, lines of C# (no blank lines, comments or generated code), comment lines, tests, XAML, the reading time for a careful review at 200–400 lines an hour, and findings per 1,000 lines of C#, for the app and its tests apart; findings in build, CI and config files are counted on their own, outside the density. Native calls, and whether a project switches on `AllowUnsafeBlocks`.
- **Projects**: each project, what it builds and how big it is.
- **Dependencies**: NuGet packages with their versions, referenced DLL files, project references and CI actions: every supply-chain link you take on with the repo.
- **Black boxes**: compiled code (by its header: PE, ELF, Mach-O, WebAssembly, Java; a file that starts with `MZ` but has no valid PE header is called out as malformed) and archives inside the zip, with their size and SHA-256. Whatever they do is hidden from the report.
- **Web addresses**: every address the shipped code and its configuration name, plus addresses the code hides and the scan worked out (marked decoded or assembled). An `HttpClient` `BaseAddress` that no relative request uses is marked as likely never contacted. Tests, comments and XML namespaces aren't counted (`xmlns` in text, `XNamespace`, `AddNamespace`), nor text that only looks like an address (`https://…`, a host with a hole in it): an address needs a real host.
- **Not covered**: what the scan can't see: other languages, files too large to read, code left out of the build, packages.

## The window

**Header.** The name and what the app does; in the centre, the pills; on the right, the version, the SDK it was built with and the runtime it runs on.

The header says what needs attention now; the findings below say what was seen. So the header's colours mean "look at this" (red), "nothing of the kind" (green) or "worth knowing" (amber), while each kind of finding keeps its own colour in the list and its filter pill, whatever its count: "Opaque 3" is red in the header and orange below.

| Pill | Shows |
| --- | --- |
| Scan 4.2 s | How long the scan takes, in seconds under a minute and as 01:12 above: amber while it runs, grey afterwards. |
| Obscured 3 · 2 decoded | Findings written so the source doesn't show them plainly: red when there are any, green at zero. "Decoded" counts those whose value the scan worked out. |
| Opaque 2 | Findings whose behaviour the source can't show by nature: red when there are any, green at zero. |
| Admin | Only when the app gets administrator rights, in amber: Windows asks for them, so they're declared, but worth knowing before it runs. A click on a pill opens Findings with what it counts: **Obscured** and **Opaque** light their filter pill; **Admin** shows what gives the app administrator rights (the manifest, `runas`); **Writes** shows the passages that write or delete; **Paths** shows the same passages sorted by the place they write to. The last three use the bar above the list, like **Show these** on the Overview. Whatever tab the jump starts from, the bar has **Back to Overview** or **Back to Facts**, which returns to that tab scrolled to where you were.

**Overview.** The first tab, in plain words for someone who doesn't read code, the technical term in brackets. It opens with one short sentence on what's worth knowing together, each of those named below it with whether the README declares it, then plain questions, each with a dot: green for a plain no, amber for worth knowing, red where the answer rests on code written to be hard to read or on a server deciding what runs. The questions: does it need administrator rights (and whether the README declares it), does it start on its own, does it change things for everyone on this computer (security settings first), does it go on the internet (when it has no connection of its own but starts a program that goes online by what it's told to do, it says so: "Not itself: no connection of its own. But it starts dotnet (publish), which downloads packages from nuget.org when they're missing; and it opens 2 web pages in your browser": dotnet with restore, build, publish, run, test, pack, tool, workload or add; git with clone, fetch, pull, push; curl, wget, winget, choco, scoop, npm, yarn, pnpm, pip, nuget; PowerShell's web cmdlets, each only where the source shows the program and what it's told), is anything hidden in the code (which also counts the places the scan didn't trace: not hidden, but not shown either), does the README say what it changes (administrator rights count, beside the combinations it could declare, and it names what it could also declare: other programs, the whole computer, the network; where the author writes about security, in a SECURITY.md or a README section headed Security, Security model or Threat model, it points there: "The author writes about security in SECURITY.md." Only a pointer: what it says isn't read or judged, and it changes no answer, finding or count. Some apps are only as safe as what a person aims them at, a crawler's target say, and that can't be seen from outside). A hive mounted with `RegLoadKey` counts as a change for everyone. Writes and deletes in a place the user chooses are said once, with what goes there: "writes and deletes in a folder you choose (NTUSER-{}.DAT; SOFTWARE, SYSTEM, SAM or SECURITY)"; reading the SAM or SECURITY hive is added ("It reads the SAM and SECURITY hives (local accounts' password hashes, the system's stored secrets) and can save registry hives to files."). Places the scan didn't trace are called that, never "decided while it runs". "Who decides" names each way the user decides (a file you pick, files you drop onto the window, what you type) and how many calls the scan couldn't trace. A change the scan couldn't trace reads "deletes files the scan couldn't trace (file:line)"; places and different changes are counted apart ("67 places in the code change the whole computer, 46 different changes: … and 42 more"); PowerShell counts scripts and commands apart ("8 scripts with 11 commands: … and 8 more"); places are cut at a word, and addresses of one kind are said once ("2 addresses decided while it runs (one ending in /robots.txt)"). Then what it reads and what it changes, area by area, changes on the right because they can do more harm:

| Area | How far |
| --- | --- |
| Registry | whole computer (HKLM), your account (HKCU) |
| Group policy | whole computer (machine policy: `…\Policies\…` under HKLM, `Machine\Registry.pol`), your account (user policy), and the policy tools `gpupdate`, `secedit`, `auditpol` |
| Files | whole computer (Program Files, ProgramData, Windows), your account (your profile, temp), its own folder |
| Internet | addresses outside the local network |
| Local network | private addresses (10.x, 172.16–31.x, 192.168.x, localhost), shares, sockets, listening for connections |
| Internet or local network | an address the code is given while it runs, wherever it points |
| Programs | PowerShell (each script by what its commands do, and how it runs: `-ExecutionPolicy Bypass` reads "script restrictions off"), system tools (`netsh`, `reg`, `schtasks` …), other programs, and code it loads |

Each area has its icon beside its name (a file, the registry, a shield for group policy, a globe for the internet, linked nodes for the local network, a window for programs, a prompt for PowerShell, brackets for code it loads). The icons are the kit's own line drawings, always next to the word, never instead of it. A policy key counts under group policy only, so the totals add up. Lines with nothing in them are left out. Every answer and every cell has **Show these**: it opens Findings with exactly those findings and a bar that says so, until **Show all**, a pill or a search. The buttons have one width, and a row without one keeps its room, so the rows stand evenly.

**Worth knowing together.** Findings that mean more together, most serious first. A combination claims a flow only where a trace shows it; two findings in the same code without a path between them aren't one.

| Combination | When |
| --- | --- |
| Runs as administrator code another program can plant | The app always runs as administrator (its manifest) and loads or starts code from a place any program running as the user can write to: the temp folder, AppData, Downloads, the Desktop, Documents, HKCU. For a program only the program itself counts: `dism.exe /MountDir:"%TEMP%\…"` mounts into the temp folder, it doesn't run anything from it. Can't be declared. |
| Building runs … with a secret present in CI | A build target of the repo's own (`Exec`) runs on every build, and a CI step builds with a secret in its environment. The build step gets a note naming the secret. |
| Hidden on purpose | Every passage written so the source doesn't show it plainly, each with what it does and how it's hidden. Can't be declared. |
| Changes security settings | The firewall, Defender, audit policy, UAC, Remote Desktop, boot settings. |
| Starts itself with Windows / Starts a program on its own | Run keys, the Startup folder, scheduled tasks, services; "itself" where what's registered is the app's own exe (`Environment.ProcessPath`), with the number of ways. A registry helper that writes many keys, a Run or RunOnce key among them, reads **May start a program with Windows**, and the Overview answers "Possibly": the source shows the key is reachable, not which call writes it. |
| Fetches code and runs it | A start or a load whose value comes from a download: directly (`Assembly.Load(await http.GetByteArrayAsync(u))`), through a file written with downloaded bytes or by `DownloadFile` and then started, or a script that downloads and runs. |
| Runs code the source doesn't show | Opaque starts and loads in the app, each with what decides it (the command line, a file's contents). |
| Sends out what it reads | A request that sends something it read (the Windows user name, a file). |
| Runs code from the projects it builds | It starts `dotnet build`, `publish`, `run`, `test` or `pack`, or `msbuild` on a project decided while it runs (a folder or zip you give it, or what it finds), not one the repo names. Building runs that project's own build steps, and a project file can run any command. |
| Building runs code from outside the repo | CI steps that download and run a script (`curl … \| bash`) and third-party actions not pinned to a commit. |

For each, the README is read. The section is headed `## Before you build or run it` (any heading level, any letter case; it ends at the next heading of the same or a higher level; examples inside code blocks don't count), with one bullet (`-`, `*` or `+`) per topic, starting with a bold label and its colon (`**Label:**` or `**Label**:`): **Needs administrator rights:**, **Changes security settings:**, **Starts on its own:**, **Runs code from outside the app:**, **Runs code when you build:**, **Starts other programs:**, **Changes the whole computer:**, **Talks to other computers:**, **Reads or sends personal data:**. A matching line makes a combination **declared in the README**, quoted with its line, in a neutral tag: a declaration tells you the author meant it, not that it's safe, so it changes how surprising a combination is, never its place in the order or the colour of its findings. A security line that doesn't name every area the code changes reads **partly declared**, with what's missing. Without the section, the rest of the README, the Markdown under `docs/` and the project's `<Description>` are searched, and a mention reads **mentioned, not declared**; it takes a phrase that names the topic ("scheduled task", "plugin", "self-update"), not a word any README has ("extension", "script", "startup"). Nothing found reads **not declared**, and a repo without a README says so. AppConsistency checks the same section and labels in its own rule, so the two apps agree.

**Before building.** The AI report and the PDF end the combinations with what to read first, by when it runs: what runs when you build (build targets), what runs in CI (with any secret a build step sees), the black boxes the build uses, then what runs when you start the app.

**Open zip…** reads a zip; dropping one on the window does the same. A zip named on the command line is read at start. Both a single wrapper folder (GitHub's `Repo-main/`, or a folder named after the app) and a zip without one work.

**Findings.** Each finding says, in plain words, what its kind is ("Reflection: code that looks up parts of a program by name while it runs…"), who decides what it does, and for reflection what it can look inside: only the app's own types, or any type including Windows' own. The combinations come first, as a group of their own (**Together**), each listing its findings with their keys; search a key to open one. Filter pills for Together and legibility (Obscured, Opaque, Untraced, Run time, Clear), scope and direction (Reads, Changes, Sends, Receives, Runs): each is the pill or tag the list shows, with its count, zero included. A pill at zero can't show anything, so it's disabled: grey, its colour taken out (colour means there's something here) but readable, its tooltip says "none in this repo", and it comes back when its count does (test code switched on, another repo). A lit pill stays clickable even at zero, so it can always be turned off. With none lit, everything shows. Lit pills in one row add up (Opaque or Untraced); the rows narrow each other (and Admin scope, and Sends); a finding with two directions passes when either is lit; while a row has a lit pill, the others in it are dimmed. A search over files, targets and what findings do, and a switch for tests. The list is grouped by scope, widest reach first; within a group, obscured first, then opaque, untraced, run time and clear. Each row's headline starts with the icon of what it touches, and the detail's kind tag carries the same icon. The list and the code beside it split 2 to 3; drag the gap between them to give either more room (the arrow keys move it too once it has the focus), double-click it for 2 to 3 again. Where it was isn't saved. The selected finding shows what it does, where, its target, where it's decided, a helper's calls, notes, the code around it (the whole member for opaque and untraced findings), with keywords, types and namespaces, strings, numbers and comments coloured, and where its target comes from.

**Copy for AI** puts the whole report on the clipboard as Markdown for an AI assistant, for a second opinion or a close look at the opaque items. It opens with the task and how to weigh the scan, names the zip's SHA-256, then the summary, the Overview as someone who doesn't read code sees it (each question and answer with the keys behind it), the combined findings with what the README says and the list for before building, the facts and every finding with its code and trace: obscured first, then opaque, untraced and run time. Numbers in it are always written 61,002 and 4.0, whatever the machine's language, so an assistant can't misread them. Up to about 400,000 characters: larger reports keep opaque and untraced findings in full and shorten the rest: findings in tests are counted per file, and every other finding becomes one line that still says what decides it, in full. **Copy this one** does the same for the selected finding.

**PDF report…** shows the report as it prints, light on white, text only, and saves it as a PDF: a first page in plain words (the Overview: the sentence, the questions, what it reads and changes, what's worth knowing together, and what the words mean), then the list for before building, the summary, every obscured, opaque and untraced finding in full with its code (keywords bold, comments grey italic, so it prints in black and white), run-time ones with their reasons, clear ones and tests in tables, the facts, and a review section to sign. Every page names the zip's SHA-256, so the PDF records exactly what was looked at. The PDF is written by the app itself, from the same pages as the preview, and it is the full report, meant for archiving: a large repo makes hundreds of pages. Laying them out and saving them run under the busy overlay, a few pages at a time, so the window stays responsive; it counts the pages and **Cancel** stops it. A stopped save writes nothing, and an existing file of that name is left as it was.

The PDF can be navigated. The first page has the contents, each line a link to its section; the bookmarks beside the pages list every section, its sub-headings and every finding written out in full (closed under their section, so the list stays short until you open one); and a finding's key wherever it appears (under each combination on the first page) jumps to its card or its row in a table. The contents have no page numbers: the links do that work. The writer is general: a block of any FlowDocument tagged with a `PdfAnchor` (an id, a title, a level) is a place, a hyperlink to `#id` jumps there, and levels 1 and 2 become bookmarks. A place is only found where a line of text starts, and text drawn on a page outside the document (a footer, marked `PageFurniture`) is never searched, so a heading's words elsewhere can't catch its bookmark.

## What it writes

Nothing, unless you save a PDF: no settings file, nothing in AppData, the temp folder or the registry. The same zip gives the same findings on any machine. One thing comes from .NET, not the app: a single-file exe built with `IncludeNativeLibrariesForSelfExtract` unpacks its native WPF libraries on first start to `%TEMP%\.net\RepoLegibility\<hash>\`.

Every pattern runs with a two-second limit, so source crafted to make a pattern run forever can't stall a scan; a passage that hits it is listed under Not covered.

## Building

```
dotnet publish RepoLegibility/RepoLegibility.csproj -c Release -r win-x64 --self-contained true
```

No third-party packages. The publish settings (single file, native libraries included, compression, no debug information, deterministic, no commit hash in the version) are in the csproj.

Code excerpts are coloured with the kit's five syntax brushes (`Brush.Syntax.*`, the guide's "Code in an app"): C# by keyword, type and namespace, string, number and comment; project files, manifests and other XML by tag name, attribute, value and comment. The PDF marks the same for print without colour: keywords and tag names bold, comments grey italic. The C# lexer (`Core/CSharpLexer.cs`) is shared with AppConsistency and copied unchanged. The PDF writer (`Core/Pdf`, `Pdf`) comes from CrawlerSuite. The theme, the filter pills and the busy overlay are HueTheme kit 1.1.5, family Cyan, unchanged. Types are told apart without a compiler, by where a name stands, so a capitalised property can be coloured as a type too.

## Versioning

`<Version>` in `RepoLegibility.csproj` is shown in the header. Major and minor stay fixed; only the build number goes up, with every delivery.
